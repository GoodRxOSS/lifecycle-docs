Do not assume that all Lifecycle component versions are compatible. A complete
version matrix, deprecation window, and rollback guarantee are not available.

## Compatibility limits

- Use the component versions that the same umbrella-chart release bundles or
  explicitly tests.
- Validate `lifecycle.yaml` with your deployed Lifecycle version. Use that
  result for the deployment.
- Do not use an older CLI schema as proof that a newer server accepts a
  configuration.
- Do not roll an application binary back across a database migration unless the
  release explicitly supports it.

## Before an upgrade

1. Record the chart, application, UI, identity service, and CLI versions.
2. Read the release notes for configuration, API, data, and security changes.
3. Identify required data or Secret migrations.
4. Back up the matched application data, configuration, and key material.
5. Test the upgrade with representative data and enabled features.
6. Test the documented rollback or restore checkpoint.

## Sites access control upgrade

Private Sites requires matched API, gateway, UI, CLI, and chart versions.
An older component does not enforce the access-control checks that a newer one expects.

The migration preserves existing sites as public.
Those sites have no assigned owner and cannot be changed through normal user controls.
New user uploads default to private.
Service-key uploads remain public and belong to the exact creating key.
Email invitations and viewer or editor roles are not available.

First, test the matched release in an isolated deployment:

1. Prepare the [Sites configuration](/docs/operations/configuration#sites-configuration).
2. Complete the [identity checks](/docs/operations/configuration#sites-identity-configuration).
3. Enable Sites through its existing core configuration setting.
4. Test owner access, unrelated-user denial, publication, privatization, expiration, deletion, and logout.
5. Verify that disabled users and revoked tokens cannot obtain new private access grants.
   Verify that existing browser grants expire within five minutes and no later than their authorizing JWTs.
6. After privatization, verify that the old content hostname stops serving content.

For production, schedule a maintenance window:

1. Back up the database, private object storage, configuration, and Secrets together.
2. Before replacing workloads, configure the UI origin and existing read-only identity client.
3. Verify that configuration.
4. Disable Sites through its existing core configuration setting.
5. Suspend reconcilers that could restart older workloads.
6. Block Sites requests, including internal uploads and content requests.
7. Drain requests.
8. Stop every older API writer, worker, and gateway.
9. Before any new core image starts, verify that all older instances have stopped.
10. Start one compatible API instance.
11. Verify migration completion.
12. Replace every remaining API, worker, gateway, and UI instance with the compatible version.
13. Verify directory access and denial of Sites content while Sites is disabled.
14. Verify that no old gateway or direct bucket URL can serve content.
15. Upgrade CLI clients.
16. Replace personal API keys that lack identity binding.
17. Enable Sites through core configuration while requests remain blocked.
18. Repeat the isolated access tests through a restricted operator test path.
19. After the tests pass, permit traffic.
20. Resume reconcilers with the compatible configuration.

Core startup runs the migration even when Sites is disabled.
An ordinary rolling image upgrade does not stop older writers before that migration.
Checks with Sites disabled cannot verify authorized private access.

If migration fails, keep traffic blocked.
If access tests fail, disable Sites.
This stops public and private Sites access.
Keep Sites traffic blocked until access tests pass.
Keep compatible core and gateway images, the schema, Redis, and the existing identity configuration during recovery.

Older clients that fetch the configuration cache need an upgrade.
That endpoint now requires administrator authentication.
Sites clients must use the capabilities endpoint.
Concurrent replacement can return `409`, including for older clients without revision fields.
Fetch current site details before you retry a change.

If private Sites must stay private, keep the access-control schema and a compatible gateway.
Disable Sites while you fix the release.
This preserves private status and denies all Sites content access.

The Sites access-control migration also supports an intentional full downgrade.
An older gateway serves active, unexpired Site content without an ownership check.
The same content URL becomes public after a full downgrade.
The downgrade removes visibility, owner identity, creator-key identity, revision fields, and personal-key issuer binding.

It keeps Site rows, Site versions, and stored files.
After a later upgrade, every surviving Site becomes public and unassigned.
Personal API keys must be replaced before they can manage Sites again.

For a full downgrade:

1. Confirm that making all active Site content public and losing ownership metadata is acceptable.
2. Back up the database and Site object storage together.
3. Block Site uploads and content requests.
4. Stop all core API, worker, and gateway instances.
5. Stop reconcilers that could restart a new core instance.
6. Verify that `035_sites_access_control.ts` is the latest applied migration.
7. Start a one-off maintenance container with the candidate core image and database configuration.
8. Bypass its normal startup command.
9. Run this targeted migration command once:

   ```bash
   pnpm exec tsx node_modules/knex/bin/cli.js migrate:down 035_sites_access_control.ts
   ```

10. Verify that the migration completed and Site and version counts did not change.
11. Deploy the matching older core, gateway, UI, and CLI versions.
12. Before you permit Site traffic again, verify the expected public access.

Do not use `pnpm db:rollback` for this step. It reverses an entire migration batch, which can contain other changes.
Do not start a new core image after the down migration. Its startup would apply the migration again.

For a UI rollback, retain compatible sign-in and site-opening behavior.
Otherwise, disable Sites before the UI rollback.
Verify that private content is unavailable before you replace the UI.
Use the privacy-preserving recovery path or the intentional full downgrade above.
You can also restore the complete pre-upgrade backup in isolation.

Use [Day-two operations](/docs/operations/day-two) for the full procedure.
